# Updating the kit from the maintainer's own setup

The kit mirrors a real, personal setup (a dashboard/tooling repo + a vault + a notes
repo). Improvements happen there first, then get exported here. The export is
mechanical so it can be repeated safely:

1. **Allowlist.** `scripts/export-from-source.sh` copies only named app/tooling files
   (dashboard, launcher scripts, Notes page + vendored JS, the notes tests, the notes
   repo's `.notes/sync.sh` and agent-setup prompt). Nothing else from the source is
   read: no vault, no notes content, no git history.
2. **Generalize.** Every copied file goes through `scripts/generalize.py <mode>`, which
   applies the maintainer's **private rules** (personal categories → `.env`-driven
   config, names/repos/machines → placeholders) and fails if a rule no longer matches
   or a personal string survives.
3. **Privacy check.** `scripts/privacy-check.sh` scans the whole kit (tokens, keys,
   e-mails, home paths, private denylist; gitleaks/trufflehog when installed).
4. **You review and commit.** The script never commits.

## One-time setup (maintainer)

```bash
mkdir -p ~/.config/task-dashboard-kit && chmod 700 ~/.config/task-dashboard-kit
cp scripts/rules.example.py ~/.config/task-dashboard-kit/rules.py
"$EDITOR" ~/.config/task-dashboard-kit/rules.py
```

In `rules.py`, add your personal strings and their replacements.

```bash
"$EDITOR" ~/.config/task-dashboard-kit/denylist.txt
```

In `denylist.txt`, put one extended regex per line: your names, project names, repos, machines, e-mail.

Both files stay **outside every repository** (they quote the personal text they
remove). Paths can be overridden with `KIT_RULES` and `KIT_DENYLIST`.

## Each export

```bash
cd ~/task-dashboard-kit
git pull
scripts/export-from-source.sh <path-to-your-tooling-clone> <path-to-your-notes-clone>
git diff --stat
git diff
uv run --with pytest pytest -q tests/
git commit -am "export: <what changed upstream>"
git push
```

`git diff` is where you review. The tests include the privacy check.

**If the export stops** with `rule matched 0x (expected 1)`, the source changed around
that spot: open `rules.py`, adjust that rule to the new source text, re-run. With
`personal strings left: …`, the source gained a new personal reference: add a rule
for it (and a denylist line if it's a new name).

## What is generated vs. kit-owned

| Generated by the export (don't hand-edit) | Kit-owned (edit here) |
|---|---|
| `app/dashboard.py` | `README.md`, `AGENTS.md`, `CLAUDE.md`, `.gemini/` |
| `app/static/**` | `docs/**` |
| `scripts/open-dashboard.sh` | `templates/vault/**`, `templates/notes/` sample content |
| `scripts/install-windows-shortcuts.sh` | `skills/**` |
| `tests/test_notes.py` | `scripts/link-notes.*`, `init-data-repos.sh`, `install-skills.sh`, `privacy-check.sh`, `generalize.py`, `export-from-source.sh` |
| `templates/notes/.notes/sync.sh`, `agent-setup-prompt.md` | `tests/test_kit.py`, `.env.example` |

If you add a new file upstream that the kit should have, add it to the allowlist in
`export-from-source.sh` (with a mode, and rules if it contains personal text). If you
add a new setting, document it in `.env.example`.
